# 06 · 深能力与知识库集成

> 面向 v1.1.0：本包从「问数」升级为「问数 + 深度分析 + 知识增强 + 报告交付」。
> 本文说明**能力边界、数据流、三个 MCP Server 在生产环境（内网「腾睿work」/ AgentScope）的注册方式、端到端示例、引用合规边界与已知限制**。
>
> 契约事实源：`spec/analysis-tools.json`（7 个分析工具）、`spec/analysis-bundle.schema.json`（分析输入数据包）、`spec/interfaces.json`（26 个 PMS 数据接口）、`manifest.json`（12 个技能）。
> 本文中的工具名、字段名、技能名全部逐字引用上述契约；**知识库工具名不写死**（以腾睿work 平台实际配置为准，见 3.5）。

## 一、能力地图

变电专业从「查数据」到「出报告」的完整链路共 7 级能力。本包 v1.1.0 的 P0 范围如下（✅ 已实现 / 🚧 后续）：

| 级别 | 能力 | 用户问题形态 | 承载者 | 状态 | 说明 |
|---|---|---|---|---|---|
| L1 | **问数**（设备是什么） | 这台主变型号/容量/投运时间？这个站有哪些断路器？ | 6 个业务技能 + 26 个数据 MCP 工具 | ✅ P0 | 台账、设备树、缺陷隐患故障、检修试验、可靠性、资源拓扑 |
| L2 | **指标**（怎么样，可量化） | 缺陷率多少？检修计划完成率？可开放容量还有多少？ | `compute_device_metrics`（派生指标） | ✅ P0（部分） | 已实现缺陷率/危急未闭环/超期未消缺/检修计划完成率/修试完成率/负载率/可开放容量比/可用率；**指标库与口径字典**列入后续 |
| L3 | **诊断**（为什么，找原因） | 这台主变为什么反复渗油？缺陷是不是家族性问题？ | `substation-diagnosis` + `diagnose_equipment`、`detect_defect_patterns` | ✅ P0 | 跨域证据链、根因假设排序（带置信度）、重复/家族缺陷簇、缺失证据清单 |
| L4 | **评估**（有多严重，打分） | 这台设备健康度几分？这个站哪些设备风险高？ | `substation-health-assessment` + `assess_device_health`、`assess_station_health` | ✅ P0 | 确定性评分卡（维度权重、扣分证据、数据完备度、置信度），站级聚合与风险 TopN |
| L5 | **预测**（会怎样，趋势） | 未来半年这台主变缺陷会不会增加？明年会不会过载？ | —（`compute_device_metrics.trend` 预留字段） | 🚧 后续 | **历史数据仅约 2 年**，样本不足以支撑可靠趋势/预测；当前 `trend` 返回 `null` 并写入 `dataGaps`，不用推测值填充 |
| L6 | **决策**（该怎么办，处置） | 先修哪台？该安排什么检修策略？ | 规则库 `suggestions` + 报告专家 | ✅ P0（规则建议）/ 🚧 后续（优化决策） | 当前输出**规则驱动的处置建议**（来自 `config/diagnosis_rules.json` 与评分卡），不是运筹优化；排序与检修策略优化列为后续 |
| L7 | **报告**（怎么呈现） | 出一份设备健康画像 / 站级月报 / 故障复盘 | `substation-report` + `generate_report`、`list_report_types` | ✅ P0 | 三类模板（`device_profile` / `station_monthly` / `fault_review`）+ 知识库引用列表 |

> 预测、优化决策、实时量测属于**有意延后**（触发条件见 [05-架构设计](05-架构设计.md) 第五节），不在 v1.1.0 的 P0 承诺内。

## 二、总体数据流

三个 MCP Server 串成一条链：**数据 MCP 取数 → Agent 组装 bundle → 分析 MCP 计算 → 知识库 MCP 检索 → 报告渲染**。

```
用户问题（腾睿work / AgentScope 会话，自然语言）
   │
   ▼
L1 编排：identify.md + substation-qa-orchestrator（意图识别 → 路由 → 设备主键归一）
   │
   │ ① 取数：数据 MCP「pms-gateway-mcp」26 个工具（Mock 或真实中台网关）
   │    get_asset_by_id / list_psr_by_filters / get_device_tree_nodes
   │    inquire_defect / list_hazard / list_fault_trip_records
   │    get_repair_plan / find_repair_test / list_patrol_record
   │    query_open_capacity / query_station_scale_analysis / ...
   ▼
② Agent 按 spec/analysis-bundle.schema.json 组装设备数据包 bundle
   （device 必填；defects/hazards/faults/tests/repairPlans/patrolRecords/load/reliability 按需；
     sourceMeta 记录每个数据来源的接口编码 interfaceCode 与调用参数；缺失段落留空，不补推测值）
   │
   ▼
③ 分析 MCP「substation-analysis-mcp」7 个工具（纯 Python 确定性计算：无网络、无凭证、同输入同输出）
   assess_device_health / assess_station_health / diagnose_equipment /
   detect_defect_patterns / compute_device_metrics / generate_report / list_report_types
   → 输出 score/grade/deductions/evidence/hypotheses/confidence/dataGaps/knowledgeQueries
   │
   │ ④ 知识增强（可选）：把 knowledgeQueries 逐条交给知识库 MCP
   │    知识库 MCP（WeKnora，平台已建好并调通；工具名以平台实际配置为准）
   ▼
⑤ citations：[{title, source, snippet, kbId}]（片段保真，不改写）
   │
   ▼
⑥ generate_report(report_type, payload, citations) → Markdown 报告
   （device_profile / station_monthly / fault_review）
   ▼
交付：分析型五段式结论（结论 → 评分/假设 → 证据链 → 置信度与缺口 → 建议）
      或 Markdown 报告 + 数据来源清单 + 知识引用列表
```

### 2.1 三层 MCP 的职责边界

| 层 | MCP Server | 职责 | 明确不做 |
|---|---|---|---|
| 数据层 | `pms-gateway-mcp`（26 工具） | 经中台网关鉴权后取数、分页、错误归一、Mock | 不做业务判断、不做计算、不组装 bundle |
| 分析层 | `substation-analysis-mcp`（7 工具） | 评分、规则匹配、聚类、派生指标、模板渲染 | 不取数、不访问网络、不读凭证、不调知识库、不猜缺失值 |
| 知识层 | WeKnora 知识库 MCP（平台配置） | 按查询语句检索规程/标准/反措片段 | 不参与任何数值计算、不生成业务结论、不改写原文 |

### 2.2 bundle 组装映射（数据工具 → bundle 字段）

| 数据 MCP 工具 | 接口编码（示例） | bundle 字段 | 组装要点 |
|---|---|---|---|
| `get_asset_by_id` / `list_psr_by_filters` / `get_device_tree_nodes` | `pgp-102-2411-00102` / `pgp-101-2411-00102` / `pgp-101-2411-00503` | `device` | `name` 必填；尽量回填 `psrId`/`assetId`/`utcNum`/`stationId`/`voltageLevel`/`deviceType`/`model`/`manufacturer`/`commissioningDate` |
| `inquire_defect` | `pgp-106-2411-00703` | `defects[]` | `level` 保持接口原枚举（危急/严重/一般）、`status`（待处理/处理中/已消除）、`discoverTime`、`closeTime`、`part`、`desc` |
| `list_hazard` | `pgp-106-2411-01003` | `hazards[]` | `type`、`riskLevel`、`status`、`desc` 原样保留 |
| `list_fault_trip_records` | `pgp-106-2411-02603` | `faults[]` | `time`、`protectionAction`、`cause`、`description` |
| `find_repair_test` | `pgp-106-2411-05003` | `tests[]` | `testType`、`testDate`、`result`（合格/不合格/异常）、`dataSummary`、`items[]` |
| `get_repair_plan` | `pgp-106-2411-04206` | `repairPlans[]` | `planId`、`planName`、`planTime`、`status`、`deviceName` |
| `list_patrol_record` | `pgp-106-2411-00403` | `patrolRecords[]` | `patrolTime`、`result`、`abnormalities[]` |
| `query_open_capacity` | `pgp-108-2411-00201` | `load` | `ratedCapacityMVA`、`currentLoadMVA`、`openCapacityMVA`、`loadRate`（百分比数值，70 表示 70%） |
| `query_station_scale_analysis` | `pgp-108-2411-00405` | `reliability` | `availabilityRate`、`outageHours`、`outageUserHours`、`statPeriod` |
| 上述任一调用 | 对应 `code` | `sourceMeta[]` | `interfaceCode`、`tool`、`calledAt`、`params`（用于证据链与可信度说明） |

**组装纪律**（与 `identify.md` 步骤 5 一致）：

1. 只放接口真实返回的字段，不加工、不补齐、不换算单位；枚举保持接口原样。
2. 列表过大先截断，并在 `sourceMeta` 记录「已截断/总数」。
3. 接口返回空 → 对应段落留空（可省略），由分析引擎输出 `dataGaps` 与降低置信度；**禁止用推测值凑齐**。
4. `timeWindow` 写明本次取数覆盖范围；`timeWindow.end` 是评分卡判定「超期未消缺/试验超期」的时间基准之一。

> bundle 由 **Agent（LLM）按 schema 组装**，这是一条明确的设计取舍：分析引擎保持纯函数式，不承担取数与时序编排（见 [05-架构设计](05-架构设计.md) D9）。

## 三、三个 MCP Server 在腾睿work / AgentScope 的注册

### 3.1 注册方式总览

腾睿work（AgentScope 智能体平台，含前端管理界面）通过 **stdio MCP** 挂载本包的能力。三个 Server 的定位与启动入口：

| Server | 传输 | 启动入口（相对 `expert-pack/`） | 依赖 | 工具数 |
|---|---|---|---|---|
| `pms-gateway-mcp` | stdio（换行分隔 JSON-RPC 2.0） | `skills/pms-gateway-mcp/scripts/mcp_server.py` | Python 3.9+，默认 Mock 无需网络 | 26 |
| `substation-analysis-mcp` | stdio（换行分隔 JSON-RPC 2.0） | `skills/substation-analysis-mcp/scripts/analysis_mcp.py` | Python 3.9+，纯本地计算 | 7 |
| 知识库 MCP（WeKnora） | stdio / 平台托管 | 平台侧已配置好，保持原样即可 | WeKnora 知识库与平台连接 | 以平台为准 |

在腾睿work 前端的一般操作路径：**工具 / 插件 → MCP Server → 新增 → 传输方式选 stdio → 填写命令、参数、环境变量 → 测试连接 → 保存并在智能体中启用**。
不同版本的菜单名与字段名可能不同（如「MCP 管理」「工具连接」「外部工具」），**以平台实际表单为准**；本包只要求语义等价：命令 = Python 可执行文件、参数 = 脚本绝对路径、环境变量 = 下表所列。

> 关键约束：`mcp_server.py` / `analysis_mcp.py` 的 **stdout 只输出协议消息**，日志走 stderr。若在宿主侧套包装脚本，务必不要向 stdout 打印任何内容。

### 3.2 数据 MCP（pms-gateway-mcp）

环境变量（事实源：`skills/pms-gateway-mcp/scripts/pms_client/config.py`）：

| 变量 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `PMS_AUTH_MODE` | 否 | `mock` | `mock` / `none` / `appkey` / `token`；联调与演示用 `mock` |
| `PMS_GATEWAY_BASE_URL` | 真实环境必填 | 空 | 中台网关完整地址，如 `https://pms-gateway.example.com` |
| `PMS_TOKEN` | `token` 模式必填 | 空 | 访问令牌 |
| `PMS_APP_KEY` / `PMS_APP_SECRET` | `appkey` 模式必填 | 空 | 应用 Key/Secret（禁止写进代码或文档） |
| `PMS_TIMEOUT` | 否 | `30` | 单次请求超时（秒） |
| `PMS_RETRY` | 否 | `1` | 可重试错误的重试次数 |
| `PMS_SPEC_PATH` | 否 | 空 | **一般无需设置**：发布 zip 已内置 `references/interfaces.json` 快照 |
| `PMS_VERIFY_SSL` | 否 | `1` | 是否校验 TLS 证书（`0` 关闭，仅限内网自签证书场景） |

`substation-analysis-mcp` **不读取任何 PMS 变量**：它不取数、不访问网关。

### 3.3 分析 MCP（substation-analysis-mcp）

- 启动入口：`skills/substation-analysis-mcp/scripts/analysis_mcp.py`（stdio，无参数）。
- **无必需环境变量**：分析引擎是纯函数式本地计算，不访问网络、不读凭证；配置来自技能内文件（见下）。
- 可选：`PYTHONIOENCODING=utf-8`（Windows 控制台/宿主日志中文兜底，PMS 侧同样适用）。
- 技能内契约资产（发布 zip 内置，构建脚本强校验）：

| 文件 | 作用 |
|---|---|
| `config/scorecard.json` | 评分卡：维度权重、各维度扣分规则、等级阈值、置信度参数（可调，改动无需改代码） |
| `config/diagnosis_rules.json` | 诊断规则库：规则 ID、关键词/条件组合、得分、处置建议、知识检索建议 |
| `templates/device_profile.md` | 设备画像报告模板 |
| `templates/station_monthly.md` | 站级月报模板 |
| `templates/fault_review.md` | 故障复盘模板 |
| `assets/demo_bundle.json` | 演示数据包（1号主变，含套管渗油**严重**缺陷、跳闸故障、不合格试验、负载率 70%），用于零依赖 demo |

- 报告类型只有三类，与 `generate_report.report_type` 枚举一致：`device_profile`、`station_monthly`、`fault_review`；用 `list_report_types` 可查所需 payload 键。

### 3.4 知识库 MCP（WeKnora，平台已配置）

知识库已在腾睿work 侧通过 MCP 调通，本包**不重复实现检索、也不定义连接参数**：

- 平台侧保持现有 WeKnora MCP 配置（地址、鉴权、知识库 ID）不变；本包不写入任何知识库凭证。
- 本包只约定**调用语义**：把分析工具返回的 `knowledgeQueries[]` 逐条检索 → 把命中片段整理为 `citations[]` → 传给 `generate_report`。
- 工具名、参数名、返回结构**一律以平台实际配置为准**；技能与文档不写死具体工具名（见 3.5）。
- 未挂载知识库 MCP 时必须降级：跳过知识增强，并在结论中注明「未引用规程条款」。

### 3.5 知识库工具名映射占位与核对方法

`knowledgeQueries` 是**语义查询**（如「油浸式变压器套管渗油缺陷定级与消缺时限」），不同知识库平台对工具的命名不同。下表是**语义槽位**，工具名为占位示例：

| 语义槽位 | 用途 | 平台工具名（占位，以腾睿work 实际配置为准） | 常见入参 | 本包期望拿到的返回 |
|---|---|---|---|---|
| `retrieve`（检索片段） | 按查询语句取 TopK 片段 | `search` / `retrieve` / `query` / `kb_search` 等（**占位，不绑定**） | `query`、`topK`（或 `limit`）、`kbId` | 片段列表（含文本、来源标题/文档 ID、得分） |
| `fetch`（取原文/上下文） | 按文档或片段 ID 取完整条款 | `get_document` / `fetch` / `read` 等（占位） | `docId` / `chunkId` | 文档标题、正文或片段上下文 |
| `list`（确认知识库） | 确认可检索的库与 ID | `list_knowledge_bases` / `list_kbs` 等（占位） | — | 知识库列表（`kbId`、名称） |

**核对与映射步骤**（一次性，由实施人员在生产环境完成）：

1. 在腾睿work 的 MCP 工具面板查看 WeKnora MCP 实际暴露的工具名与参数 schema。
2. 按上表把三个语义槽位映射到实际工具名，写入**会话级/智能体级提示词或平台配置**（不要写进本包源码，避免平台升级后失效）。
3. 用一条已知条款的查询验证：返回片段是否与知识库原文一致（片段保真），确认后再用于报告引用。
4. 若平台只提供单一检索工具，则可省掉 `fetch`/`list` 槽位；本包不要求三个槽位齐全。

**占位纪律**：文档与技能中出现 `search`/`retrieve` 等字样一律视为「常见命名示例」，实际调用以平台为准；不得因为占位名不匹配就判定知识库不可用。

### 3.6 `mcpServers` 配置示例（三种宿主通用）

Claude Desktop / Claude Code / OpenClaw 与 AgentScope 的配置结构相近，均为 `command` + `args` + `env`：

```json

      "command": "python",
      "args": [
        "F:/work/2026年/10月/专家包/expert-pack/skills/pms-gateway-mcp/scripts/mcp_server.py"
      ],

        "PMS_AUTH_MODE": "mock",
        "PMS_TIMEOUT": "30",

      }
    },
    "substation-analysis-mcp": {
      "command": "python",
      "args": [
        "F:/work/2026年/10月/专家包/expert-pack/skills/substation-analysis-mcp/scripts/analysis_mcp.py"
      ],
      "env": {
        "PYTHONIOENCODING": "utf-8"
      }
    },
    "weknora-kb": {
      "command": "<平台已配置的启动命令，保持原样>",
      "args": ["<平台已配置的参数，保持原样>"],
      "env": {
        "PYTHONIOENCODING": "utf-8"
      }
    }
  }
}
```

说明：

- 路径建议用**绝对路径**；JSON 中反斜杠写成 `\\`，或直接用 `/`。
- 若 `python` 不在宿主 PATH，把 `command` 换成 Python 绝对路径（如 `D:/App/Tool/Miniconda/python.exe`）。
- 分析 MCP 未挂载时，技能会回退到 `scripts/analysis_cli.py`（CLI 兜底，与 MCP 共用同一分析引擎）。
- 数据 MCP 未挂载时，技能回退到 `scripts/pms_cli.py`。
- 知识库 MCP 名称（上例 `weknora-kb`）只是本包示例键名，**与平台内已有配置保持一致即可**，无需改名。

## 四、端到端示例

> 以下命令在仓库根目录（`专家包/`）执行；`analysis_cli.py` 的子命令与参数以 `python expert-pack/skills/substation-analysis-mcp/scripts/analysis_cli.py --help` 为准，文档给出典型用法。
> 演示默认 Mock 数据，回答与报告必须标注「Mock 数据，仅用于联调」。

### 4.1 示例一：设备健康画像（问数 → 取数 → 评分 → 诊断 → 报告）

**步骤 1 · 取数（数据 MCP / CLI 兜底）**

```powershell
$env:PMS_AUTH_MODE = "mock"

# 台账：确认设备主键（psrId/assetId/utcNum）与基础属性
python expert-pack/skills/pms-gateway-mcp/scripts/pms_cli.py call get_asset_by_id --params '{"assetId":"AST-102-0001"}'

# 同站设备清单（用于站级画像时批量取数）
python expert-pack/skills/pms-gateway-mcp/scripts/pms_cli.py call list_psr_by_filters --params '{"stationId":"STA-220-01","deviceType":"主变","pageNo":1,"pageSize":10}'

# 缺陷 / 故障 / 修试 / 负载
```

## 五、知识增强的引用规范与合规边界

### 5.1 引用规范

1. **只引用知识库真实返回的内容**：`citations[].snippet` 必须来自检索结果原文，**不改写、不概括、不拼接**；`title`/`source`/`kbId` 与命中记录一致。
2. **每个引用可回溯**：报告中每条引用保留来源标题与片段；无法定位来源的片段必须丢弃。
3. **检索不到就明说**：写「知识库未检索到相关条款」，不得编造条款号、标准编号、条文原文。
4. **引用与数据分离**：知识库内容只用于「条款依据/处置要求」，不得用作评分、指标、缺陷率等数值的数据源。
5. **引用格式建议**：正文结论后标注 `【来源：<文档标题>；片段：<原文摘录>】`，报告末尾统一列出「知识引用列表」。

### 5.2 合规边界

| 边界 | 要求 |
|---|---|
| 不虚构 | 禁止编造规程条款、标准条文、反措要求、文件编号；检索为空即如实说明 |
| 片段保真 | 原文引用不得增删关键词、不得改变限定条件（如「应/宜/可」、时限数字） |
| 可追溯 | 每条引用必须能回到知识库中的文档与片段（`source` + `kbId`） |
| 脱敏 | 知识片段与报告中对手机号、身份证号、详细地址、人员姓名等敏感信息脱敏 |
| 不外传 | 知识库内容属内部资料，仅在内网与会话内使用；不得写入对外文档、代码仓库或发布包 |
| 权限 | 检索范围受知识库平台权限控制，不越权检索、不缓存超权限内容 |
| 复核 | 涉及停电影响、可靠性、检修决策、责任认定的结论需业务人员复核；引用条款与现场实际冲突时以现场与最新文件为准 |
| 时效 | 规程/标准存在版本更替，引用时应记录知识库返回的文档版本或检索时间；过期条款需人工确认 |

## 六、已知限制

| # | 限制 | 影响 | 应对（v1.1.0 做法 / 后续计划） |
|---|---|---|---|
| 1 | **历史数据仅约 2 年** | 同比/趋势/寿命预测样本不足，结论易受单次异常影响 | 当前不做趋势与预测：`compute_device_metrics.trend` 返回 `null` 并写入 `dataGaps`；报告中明示数据年限；后续随数据积累再启用 |
| 2 | **趋势/预测类能力延后** | 用户问「明年会不会过载/缺陷会不会增多」时无法给出定量预测 | 回答降级为「基于现有数据的事实 + 风险提示」，不下预测结论；列入后续路线 |
| 3 | **bundle 由 Agent 组装** | 组装质量取决于 Agent 对 schema 的理解；漏字段会降低置信度 | 技能内置组装映射表与示例（见 2.2、`references/bundle-schema.md`）；分析引擎输出 `dataGaps`/`completeness` 暴露缺口；禁止补推测值 |
| 4 | **规则与权重需业务校准** | 评分卡权重（缺陷 0.30/故障 0.25/修试 0.20/负载 0.15/台账 0.10）、扣分阈值、诊断规则关键词均为**初始值**，未经本省业务专家全量校验 | 全部放在 `config/scorecard.json`、`config/diagnosis_rules.json`，改配置不改代码；上线前用真实样本做回溯校准并留档 |
| 5 | **诊断规则库为启发式关键词/条件组合** | 复杂故障可能漏判或给出多条近似假设 | 输出按得分排序的多个假设 + `confidence` + `missingEvidence`，低置信度不得写成确定结论；规则持续补充 |
| 6 | **知识库工具名依平台而定** | 换平台/升级后检索工具名可能变化 | 只约定语义槽位（3.5），映射写在平台侧配置，不写死进包 |
| 7 | **无实时量测** | 「当前负载/当前状态」只能取可开放容量、可靠性等统计口径 | 台账+统计口径回答并标注数据截止时间；实时量测列入后续（见 [05-架构设计](05-架构设计.md) 第五节） |
| 8 | **默认 Mock 模式** | 演示数据为虚构样例，不能作业务结论 | 所有 Mock 输出标注「Mock 数据，仅用于联调」；真实结论必须切真实凭证 |
| 9 | **报告为 Markdown** | 不直接产出 Word/PDF，版式需后处理 | 报告正文 + 数据来源清单 + 引用列表可直接粘贴到文档系统；版式转换列入后续 |
| 10 | **接口规格为推断值** | 参数/返回字段可能与正式文档不一致 | 只改 `spec/interfaces.json`（见 [04-开发与扩展指南](04-开发与扩展指南.md)）；Mock 与真实同构 |
