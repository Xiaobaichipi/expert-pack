# 诊断专家 · 诊断解读指南

> 本文件是 `substation-diagnosis` 的细节层，供「拿到 `diagnose_equipment` / `detect_defect_patterns` 返回值之后怎么写解读」时查用。
> 事实源优先级：`spec/analysis-tools.json`（工具契约）> 分析引擎 `config/diagnosis_rules.json`（规则库）> 本文件（解读话术）。
> **规则名、规则ID、score、confidence 一律以工具返回为准**；本文的规则方向仅用于解释「为什么会命中」，不得据此自造规则或自算匹配度。

## 二、假设排序解读

### 2.1 排序与分数

- `hypotheses[]` 已按 `score` 降序排列，**原样呈现顺序**；`score` 是「证据匹配度（0-1）」，不是故障概率。
- 允许的写法：「匹配度 0.78」「排在首位」「并列两条方向接近」。
- 禁止的写法：「有 78% 的概率是套管受潮」「肯定是套管问题」「排除其他可能」（除非引擎返回了排除结论）。

### 2.2 多假设怎么讲

| 情形 | 呈现方式 |
|---|---|
| Top1 明显领先（如 0.78 vs 0.31） | 主方向 + 次要方向，说明主方向依据与待确认点 |
| 前两条接近（差值 <0.1） | 并列呈现，写「两条方向证据相当，需用 X 试验区分」 |
| 全部低于 0.5 | 只报「方向线索」，不给主因；重点转为补证据清单 |
| 假设数被 `max_hypotheses` 截断 | 注明「仅展示前 n 条（`max_hypotheses`）」，不暗示已穷尽 |

### 2.3 假设与「记录原因」的区别

`faults[].cause`（如「套管绝缘受潮」）是故障记录里的人工结论；诊断假设是引擎按证据重算的结果。两者一致时写「与记录原因方向一致」，不一致时**并列展示并说明差异**，不得以记录值覆盖诊断结果，也不得替业务下最终定性。

## 三、证据链写法

### 3.1 每条假设三段式

```markdown
1) 支持证据：差动保护动作（FT-2026-0001，2026-08-03 02:17）+ 套管渗油严重缺陷（DF-2026-0001，处理中）
   + 2025-04 预试合格但已超一个试验周期。
2) 规则与来源：规则 <ruleId>（原样引用）；来源接口 pgp-106-2411-02603、pgp-106-2411-00703、pgp-106-2411-05003。
3) 反证与缺口：缺最近一次介损与油色谱数据（missingEvidence），巡视未记录外部放电痕迹（反证较弱）。
```

### 3.2 证据表模板

| 序 | 证据内容 | 数据来源 | 接口编码 | 支持/反向 |
|---|---|---|---|---|
| 1 | 差动保护动作 | FT-2026-0001 | pgp-106-2411-02603 | 支持 |
| 2 | 套管渗油严重缺陷处理中 | DF-2026-0001 | pgp-106-2411-00703 | 支持 |
| 3 | 最近预试合格但超期 | RT-2025-0001 | pgp-106-2411-05003 | 中性/缺口 |

### 3.3 写法纪律

- 证据必须是**接口返回过的原文事实**，不改写成更专业的判语（如把「油位偏低」写成「绝缘击穿」）。
- 每条证据带记录标识（`faultId`/`defectId`/`recordId`）与接口编码，保证可追溯。
- 反向证据（巡视未见异常、试验合格）也要写，避免只挑支持证据形成「确认偏误」。
- 证据条数与 `confidence` 要对得上：只列 1 条却写「证据链完整」属于违规。

## 四、置信度处理

### 4.1 来源与分档

`hypotheses[].confidence` 由引擎按「证据条数 + 数据完备度」推导（口径以引擎实现为准，LLM 不复算）。解读分档：

| confidence | 档位 | 允许的结论强度 | 话术 |
|---|---|---|---|
| ≥0.75 | 较高 | 可作排查重点方向 | 「证据链较完整（n 条证据），建议优先按此方向现场核查」 |
| 0.55-0.74 | 中等 | 可作方向，不可定性 | 「有多条间接证据，建议补做 X 后确认」 |
| 0.30-0.54 | 低 | 仅线索 | 「仅提示方向，不能定性；需补 {缺失证据}」 |
| <0.30 | 极低 | 只报缺口 | 「现有证据不足以形成假设，先补数据（见核查清单）」 |

### 4.2 低置信度三条硬约束

1. 句子里不得出现「原因就是 / 可判定为 / 已确认」等定性措辞。
2. 必须在结论同一段内写出「需补什么证据、由谁确认」。
3. 若低置信度源于整域数据缺失（`dataGaps` 非空），先写数据缺口，再写方向。

### 4.3 如何提升置信度（写进建议，不写进结论）

按 `missingEvidence` 补：最近一次预试分项数据、油色谱、红外测温、保护录波、上次消缺验收记录、同型号设备缺陷等。补数后**重跑 `diagnose_equipment`**，不得手工上调置信度。

## 五、缺失证据 → 下一步核查清单

| 缺缺陷明细与处理过程 | 调 `view_defect` 取描述、照片、处理过程、验收 | pgp-106-2411-00704 | 缺陷时间轴 |

| 缺检修执行情况 | 调 `get_repair_plan`、`find_repair_program` | pgp-106-2411-04206 / pgp-106-2411-04803 | 计划与方案对照 |

## 六、重复缺陷（`duplicateClusters`）解读

- 含义：同一部位在 `window_days` 窗口内重复出现，达到聚类条件 → 指向「薄弱点未根治」而非偶发。
- 解读要点：
  1. 报「部位 + 次数 + 时间跨度和等级分布」；
  2. 追问上次消缺是否验收、是否更换备件、是否同工艺；
  3. 结论落成「建议将该部位纳入专项检查/状态评价重点」，不直接给「设备应更换」结论。
- 禁止：把不同部位合并成一个「重复缺陷」；把 2 次一般缺陷说成「频发缺陷」而不给窗口口径。

## 七、家族性缺陷（`familyClusters`）解读

- 含义：同型号 + 同厂家 + 同部位在设备群中达到 `family_min_count`（默认 3）→ 可能是设计、批次或工艺共性。
- 解读要点：
  1. 报「型号/厂家 + 部位 + 涉及台数 + 设备名清单」；
  2. 给「建议联系厂家、核查同批次投运设备、纳入专项排查」；
  3. 明确边界：**家族簇不等于这几台设备都已故障**，也不等于「该型号全部不合格」。
- 参数口径：`window_days` 与 `family_min_count` 的选择必须写进回答（如「近 730 天、同部位 ≥3 台」），不同参数得出的簇不可直接比较。

## 八、与健康评估、报告技能的衔接

| 下游 | 传什么 | 注意 |
|---|---|---|
| `substation-health-assessment` | 风险线索（重复/家族簇、严重缺陷） | 不传分数、不改分数；健康度由其自身工具计算 |
| `substation-report`（`fault_review`） | `hypotheses[]`（名称/匹配度/置信度）、证据表、`missingEvidence`、`suggestions` | 报告渲染由 `generate_report` 完成，本技能不拼模板 |
| `substation-report`（`device_profile`） | 诊断结论摘要（一段话 + Top2 假设） | 篇幅控制，详情放附件 |

## 九、常见误读清单

| 误读 | 正确做法 |
|---|---|
| 把 `score` 当概率 | 称「匹配度」，不换算百分比 |
| 自己重排假设顺序 | 原样呈现 |
| 只讲 Top1 | 至少呈现前 2-3 条并说明差异 |
| 把 `cause` 记录当诊断结论 | 并列展示、说明是否一致 |
| 低置信度直接下结论 | 写方向 + 补证据清单 |
| 用推测补齐缺失证据 | 列 `missingEvidence`，等数据 |
| 把家族簇写成「全部设备故障」 | 写「共性风险线索，需排查」 |
| 忽略 `max_hypotheses` 截断 | 注明展示条数 |

## 十、自检清单

- [ ] 假设顺序、`score`、`confidence` 与工具返回逐字一致。
- [ ] 每条假设都有「支持证据 + 规则/接口 + 反证与缺口」三段。
- [ ] 低置信度（<0.55）未出现定性措辞。
- [ ] `missingEvidence` 与 `dataGaps` 全部转成四列核查清单。
- [ ] 重复/家族簇写明了 `window_days` / `family_min_count` 口径。
- [ ] 知识引用有来源标注；无检索结果时写明「知识库未检索到相关条款」。
- [ ] Mock 模式已标注；未做责任认定式表述。
