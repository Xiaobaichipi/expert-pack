# 04 · 开发与扩展指南

本指南面向后续维护者：如何以契约文件为单一事实源修改接口、新增工具/技能，以及如何构建、校验和测试。架构层面的取舍见 [05-架构设计](05-架构设计.md)。

v1.1.0 起共有**三份契约事实源**：

| 契约文件 | 内容 | 消费方 |
|---|---|---|
| `spec/interfaces.json` | 26 个 PMS 数据接口（工具名/编码/method/path/参数/返回/Mock） | 数据 MCP、CLI、6 个业务技能、文档 01 第一节 |
| `spec/analysis-tools.json` | 7 个分析工具（工具名/参数/返回/设计规则） | 分析引擎、分析 MCP/CLI、3 个深能力技能、文档 01 第四节 |
| `spec/analysis-bundle.schema.json` | 分析输入数据包（bundle）字段契约 | 健康评估/诊断技能（组装）、分析引擎（校验与完备度计算） |

## 一、单一事实源：spec/interfaces.json

`expert-pack/spec/interfaces.json` 是 26 个接口的**唯一事实源**。以下内容全部由它派生，不允许另存一份字段定义：

| 派生对象 | 派生方式 | 位置 |
|---|---|---|
| MCP 工具 schema（`tools/list` 的 name/description/inputSchema） | 运行时读取 spec 生成 | `skills/pms-gateway-mcp/scripts/pms_client/spec.py` |
| 工具调用参数校验与 Mock 数据 | 运行时读取 spec | `pms_client/client.py`、`pms_client/mock.py` |
| CLI `list-tools` / `describe` / `call` | 运行时读取 spec | `scripts/pms_cli.py` |
| 12 个技能的「工具清单」表 | 编写时引用 spec 字段（人工同步，评审时核对） | `skills/*/SKILL.md`、`references/*.md` |
| 文档 01 的 26 行映射表 | 从 spec 生成（工具名/编码/地址/典型问数）+ 原始说明文档（名称/中心/能力域），人工核对 | `docs/01-接口映射表.md` |
| 构建校验（26 个工具、唯一性、group、skill 一致性） | 读取 spec 校验 | `tools/build_pack.py` |
| 底座技能 zip 内的 spec 快照 `references/interfaces.json` | 构建时由 `build_pack.py` 注入，内容 = `spec/interfaces.json` 原始字节 | 发布产物 `dist/skills/pms-gateway-mcp.zip`（构建生成件，不构成第二事实源） |

**规则**：任何接口差异只改 spec；如果发现代码里出现硬编码的 path/参数名，属于缺陷，应改为读 spec。**不要把 `interfaces.json` 手工复制进技能目录当作第二份事实源**——底座技能 zip 内的 `references/interfaces.json` 只能由 `build_pack.py` 在打包时注入（字节与 spec 一致，构建脚本会校验），它让 skillhub 单独安装底座后「装完即用」；`PMS_SPEC_PATH` 仅用于指向更新版 spec 覆盖内置快照，或本地开发调试时显式指定。

> 分析侧同构：`spec/analysis-tools.json` 是分析工具的唯一事实源（MCP `tools/list`、CLI 子命令、深能力技能的工具表、文档 01 第四节均由它派生）；`spec/analysis-bundle.schema.json` 是 bundle 字段的唯一事实源。分析引擎的评分卡/规则库是**配置**（`config/*.json`），不是契约：调权重、调阈值只改配置。

## 二、拿到官方《接口说明文档》后如何修订 spec

### 2.1 修订字段

以单个工具对象为单位，逐项对照官方文档：

| spec 字段 | 含义 | 修订要点 |
|---|---|---|
| `code` | 接口编码（如 `pgp-102-2411-00102`） | 一般稳定；若与文档不一致，以服务目录为准，并同步文档 01 |
| `name` | MCP 工具名（全局唯一，`^[a-z][a-z0-9_]*$`） | **尽量不改**：技能文档、问数话术、测试都引用它；确需改则全仓库检索替换 |
| `title` | 接口名称 | 与文档一致；同步文档 01 |
| `group` | 所属业务分组（`spec.groups[].id`） | 不改则无需动 groups；改则同步 toolCount 与文档 01 的「所属技能」 |
| `method` / `path` | 请求方式与相对路径 | 以文档为准；path 占位符（如 `{assetType}`）与 `params[].in = "path"` 必须一致 |
| `paramStyle` | `query` / `json_body` / `mixed` | GET 一般是 query；POST 一般是 json_body；path + query 混合用 `mixed`，具体由 `params[].in` 决定 |
| `params` | 参数定义（name/type/required/desc/default/example/in） | 名称、必填性、类型逐项对齐；新增分页参数时保持 `pageNo`/`pageSize` 命名 |
| `responseHint` | 返回结构提示：`kind`（object/paged/list）、`dataKey`、`listKey` | 网关层统一解包依据；paged 必须有 `listKey` |
| `mock` | Mock 模式样例响应 | 与返回结构同构；用脱敏/虚构数据，禁止真实业务数据 |
| `typicalQuestions` | 典型问数（驱动文档与技能示例） | 至少 1 条，问题要与接口能力对应 |

### 2.2 修订步骤

1. 备份/记录本次变更依据（文档版本、接口编码、确认人）。
2. 编辑 `spec/interfaces.json`，**先只改一个接口**，不要一次改 26 个；便于定位差异。
3. 更新该工具的 `mock` 与 `typicalQuestions`，保持可演示。
4. 运行校验与测试（见第六节），确认没有破坏其他派生对象。
5. 同步受影响的人工文档：`docs/01-接口映射表.md`（若名称/地址/能力域变了）、对应技能的 `SKILL.md` 工具表与 `references/queries.md`。
6. 递增 `specVersion`（如 `1.0.0` → `1.1.0`），在版本记录中写明「依据《接口说明文档》vX 修订了哪些接口」。
7. 重新 `build_pack.py` 产出并归档 checksums。

### 2.3 修订示例（仅示意，实际以官方文档为准）

```jsonc
// 修订前（推断值）
"method": "GET",
"path": "/assetCenter/queryServices/getAstById",
"paramStyle": "query",
// 修订后（按官方文档）
"method": "POST",
"path": "/assetCenter/queryServices/getAstById",
"paramStyle": "json_body",
"params": [
  {"name": "assetId", "type": "string", "required": true, "desc": "资产/设备台账ID", "example": "AST-102-0001"}
],
"responseHint": {"kind": "object", "dataKey": "data", "desc": "单个设备完整台账对象"},
```

> 注意：`jsonc` 注释仅用于文档说明，`interfaces.json` 必须是严格 JSON（不能有注释）。

## 三、新增第 27 个工具

以新增一个「一次设备试验报告」类接口为例（示例工具名 `get_test_report`，**当前 spec 中不存在**，仅用于说明流程），完整步骤如下：

1. **spec 追加工具对象**：在 `tools` 数组末尾追加完整对象（字段见 2.1），`group` 必须使用已有分组 id（或先新增分组）。
2. **更新分组计数**：对应 `groups[].toolCount` 加 1；若新增分组，补 `id/title/skill/role/toolCount`。
3. **更新构建期望值**：`tools/build_pack.py` 顶部的 `EXPECTED_PMS_TOOL_COUNT = 26` 改为 27，否则构建会以「tools 数量应为 26」失败（这是有意的防漏改）。
4. **网关层**：`call_tool(name, params)` 是统一入口，新工具自动可用；如需与其他工具一致的显式方法，在 `pms_client/client.py` 增加同名方法（方法名 = 工具名），并在 `pms_client/mock.py` 复用 spec 的 `mock`。
5. **测试**：`expert-pack/tests/` 中涉及「26 个工具」的断言改为 27；新增该工具的 mock 调用、参数校验、分页/错误用例（见第七节）。
6. **技能归属**：把工具加入对应业务技能的 `SKILL.md` 工具表与 `references/queries.md`（新能力域则新增技能，见第四节）。
7. **文档**：`docs/01-接口映射表.md` 增加第 27 行并更新按技能汇总；`README.md` 的接口数与技能表同步；`docs/05` 中涉及接口数量的描述同步。
8. **验证**：
   ```powershell
   python expert-pack/tools/build_pack.py --validate-only
   python -m unittest discover -s tests -v          # 在 expert-pack 目录执行
   python expert-pack/skills/pms-gateway-mcp/scripts/pms_cli.py list-tools
   python expert-pack/skills/pms-gateway-mcp/scripts/pms_cli.py call get_test_report --params '{"reportId":"R-0001"}'
   ```
9. **提交评审**：spec 属于全员共享契约，变更需 Lead/接口负责人确认后合入；同时确认 `manifest.json`/`identify.md` 是否需要同步（通常不需要）。

## 四、新增技能（从 12 个继续扩展）

> **技能数不硬编码**：`build_pack.py` 按 `manifest.skillSlugs` 动态读取并逐个校验，不再写死 8 或 12。当前为 12 个（2 底座 + 6 业务 + 3 深能力 + 1 总控），顺序契约：前两项必须是 `pms-gateway-mcp` → `substation-analysis-mcp`，最后一项必须是 `substation-qa-orchestrator`。

1. 新建 `expert-pack/skills/<slug>/`，`SKILL.md` frontmatter 至少含：
   ```yaml
   ---
   name: <slug>                # 必须与目录名完全一致（构建脚本强校验）
   slug: <slug>                # 必须与目录名一致（skillhub publish 必填）
   displayName: <中文名>       # 技能显示名（skillhub publish 必填）
   description: >-             # 中文，写清能力与触发词
     ...
   version: 1.1.0              # SemVer（构建与 publish 强校验）
   metadata:
     author: 国网河南院 变电智能问数项目组
     package_type: skill
     display_name: <中文名>
   ---
   ```
2. 派生 `references/queries.md` 等细节文件，避免把长内容塞进 `SKILL.md`（控制上下文成本）。
3. 若引用数据接口，工具名/编码必须来自 `spec/interfaces.json`；若引用分析工具，工具名/参数必须来自 `spec/analysis-tools.json`；**不得自造工具，也不得在新技能里重写评分/诊断计算逻辑**（计算只能由分析 MCP 提供）。
4. 更新 `manifest.json` 的 `skillSlugs`（顺序契约）——这是共享契约，需 Lead 确认；`skills[]` 由构建脚本从各 `SKILL.md` frontmatter 生成，无需手写；同步 `identify.md` 的 `orchestration.children` 与工作流/角色表。
5. 更新 `docs/01` 技能汇总（分析侧见第四节）、`README.md` 技能表、`docs/05` 架构描述、`docs/03` 发布顺序。
6. 运行构建与测试，按 [03-部署与使用说明](03-部署与使用说明.md) 第二节发布新技能，并同步更新专家包技能列表（数量与顺序）。

## 五、分析工具扩展与 bundle schema 演进

### 5.1 新增/修改一个分析工具（7 → 8）

分析工具属于分析底座契约，涉及「契约 → 引擎 → 测试 → 构建 → 文档」五处，顺序不可颠倒：

1. **改契约**：在 `spec/analysis-tools.json` 的 `tools` 末尾追加工具对象，字段与现有工具同构：
   `name`（`^[a-z][a-z0-9_]*$`、全局唯一）、`title`、`desc`、`params[]`（`name`/`type`/`required`/`default`/`desc`/`enum`）、`returns`。
   - **参数规则（构建强校验）**：`required` 必须是布尔值；`required: true` 的参数必须排在所有可选参数之前，且不得带 `default`；同一工具内参数名唯一。
   - 若新工具需要新的输入字段，先改 `spec/analysis-bundle.schema.json`（见 5.2），**不要**在工具参数里塞自然语言参数。
2. **写引擎**：在 `skills/substation-analysis-mcp/scripts/analysis/` 增加纯函数实现（无网络、无凭证；时间基准取 `bundle.timeWindow.end` 或 CLI 的 `--as-of`，仅报告 `generatedAt` 读系统时钟），并把可调阈值/权重放进 `config/*.json`。
3. **接协议**：在 `scripts/analysis_mcp.py` 的 `tools/list` 与 `tools/call` 注册工具（schema 从 `spec/analysis-tools.json` 读取，禁止另写一份描述）；在 `scripts/analysis_cli.py` 增加对应子命令。
4. **补测试**：`expert-pack/tests/` 增加该工具的正常/缺参/边界用例，并断言 `tools/list` 与 `spec/analysis-tools.json` 逐项一致（name/参数/required）。
5. **更新构建期望值**：`tools/build_pack.py` 的 `EXPECTED_ANALYSIS_TOOL_COUNT` 由 7 改为 8（防漏改），否则构建失败。
6. **同步文档与技能**：`docs/01` 第四节映射表、`docs/03` 分析 CLI 示例、相关深能力技能的工具表与 `references/`。
7. **验证**：`python expert-pack/tools/build_pack.py --validate-only` → `python -m unittest discover -s tests -v` → `analysis_cli.py demo`。

### 5.2 bundle schema 演进规则

`spec/analysis-bundle.schema.json` 是数据侧与分析侧之间**唯一的耦合面**，演进遵循「加字段宽松、改字段严格」：

| 变更类型 | 兼容性 | 规则 |
|---|---|---|
| 新增**可选**字段（如新增 `patrolPlans[]`） | 向后兼容 | minor 版本；同步更新 `references/bundle-schema.md`、组装映射表（docs/06 2.2）与相关技能；分析引擎对缺失段落必须降级（`dataGaps` + 降低置信度），不得报错 |
| 新增**必填**字段（除 `device` 外） | 破坏性 | **默认不做**：bundle 由 Agent 按需组装，必填项越多越容易产生缺口；确需必填时按 major 版本，并给出默认降级策略 |
| 修改字段类型/语义（如 `loadRate` 由百分比数值改为 0–1 小数） | 破坏性 | major 版本；必须同时改：分析引擎解析、评分卡/规则库、测试、文档 06 组装映射表；旧 bundle 需迁移脚本或显式报错说明 |
| 修改枚举（如缺陷 `level` 增减） | 视情况 | 若只是扩充枚举（新增取值），minor；若改变取值范围/含义，major，并同步 `config/diagnosis_rules.json` 的关键词 |
| 删除字段 | 破坏性 | major 版本；先确认 12 个技能与测试中无引用 |
| 调整 `required`（`device.name` 等） | 破坏性 | 需 Lead 与业务确认；`device`/`device.name` 是组装最小集，原则上不变 |

**版本记录方式**：bundle schema 的 `$id` 保持稳定；兼容性变更在 `docs/06` 第六节「已知限制」与版本记录中说明；破坏性变更必须同时递增 `spec/analysis-tools.json` 的 `specVersion` 与专家包版本（`identify.md` frontmatter）。

**禁止**：在 schema 里塞入与业务口径无关的展示字段（如颜色、排序）；把知识库条款写进 bundle（知识只走 `citations`）；用 `additionalProperties: false` 卡死上游（上游接口字段可能先于契约变化，宽松接收 + 显式忽略未知字段更稳）。

## 六、构建与校验命令

```powershell
# 全量校验 + 打包（默认 --src expert-pack --out expert-pack/dist）
python expert-pack/tools/build_pack.py

# 只校验不打包（CI / 提交前）
python expert-pack/tools/build_pack.py --validate-only

# 自定义源目录/输出目录（例如打临时验证包）
python expert-pack/tools/build_pack.py --src expert-pack --out .\dist-test

# 技能尚未齐全时临时验证流程（产物禁止正式发布）
python expert-pack/tools/build_pack.py --allow-missing
```

构建脚本会校验以下内容，任一失败以**非 0 退出并打印中文原因**：

- **PMS 契约**：`spec/interfaces.json` 的 `tools` 数量 = 26、工具 `name`/`code` 唯一、`group` 合法且 `toolCount` 一致、必填字段齐全；
- **分析契约**：`spec/analysis-tools.json` 存在、分析工具数量 = 7、`name` 唯一且合法、参数 `required` 合法（布尔、必填项排在可选之前、必填项不带 default）、`enum` 合法；
- **bundle 契约**：`spec/analysis-bundle.schema.json` 是合法 JSON，且具备 `type: object`、`required` 含 `device`、`device.required` 含 `name` 等最小结构；
- **manifest**：符合平台 SkillSet 清单契约（`manifestVersion="1"`、`type="skillset"`、`slug`/`displayName`/`summary` 非空、`skillSlugs` 非空且顺序为「两个底座在前、总控在最后」；`slug`/`displayName` 与 PMS spec 一致）；`skills[]`/`files[]` 由构建脚本生成（**技能数从 manifest 动态读取**）；
- **技能结构**：每个 `skillSlugs` 对应目录存在且含 `SKILL.md`；frontmatter 的 `name`、`slug` 均与目录名一致，`displayName` 非空、`description` 非空、`version` 为 SemVer（与 `skillhub publish` 校验一致）；
- **`identify.md`**：存在、frontmatter `name` 与专家包 slug 一致、`version` 为 SemVer；
- **分析资产**：`substation-analysis-mcp` 必须含 `config/scorecard.json`、`config/diagnosis_rules.json`、`templates/` 下 3 个模板、`assets/demo_bundle.json`，且 JSON 合法、demo 数据包符合 bundle 最小契约；**其余技能不得包含这些文件**；
- **产物**：每个 zip < 10MB（平台限制），技能 zip 根含 `SKILL.md`，专家包清单包仅含 `manifest.json` + `identify.md` 且 `files[]` 的 sha256/size 与 identify.md 字节一致。

产物（`expert-pack/dist/`）：12 个 `skills/<slug>.zip`（其中 `pms-gateway-mcp.zip` 内置 `references/interfaces.json` spec 快照，`substation-analysis-mcp.zip` 内置分析引擎契约资产）、`<pack-slug>-bundle.zip`（平台专家包清单包：构建生成的 manifest.json + identify.md）、`checksums.txt`（sha256 + 相对路径）。构建是**幂等且确定性**的：同样输入重复构建，`checksums.txt` 完全一致（zip 内时间戳固定）；构建脚本会校验底座快照与 `spec/interfaces.json` 字节一致、其余技能不含该快照。

校验产物：

```powershell
Get-Content expert-pack/dist/checksums.txt
# 逐行比对
Get-FileHash expert-pack/dist/skills/pms-gateway-mcp.zip -Algorithm SHA256
```

## 七、测试

在 `expert-pack` 目录下执行（无需 PYTHONPATH）：

```powershell
cd expert-pack
python -m unittest discover -s tests -v
# 等价：python -m unittest discover -s tests -t . -v
```

现有测试覆盖（由底座实现维护，详见 `expert-pack/tests/`）：

- spec 完整性：26 个数据工具、name/code 唯一、group 与 toolCount、必填字段；
- 客户端：`call_tool` 正常路径、未知工具、参数校验、错误归一；
- Mock：按 spec 返回、过滤与分页；
- MCP 协议：`initialize` / `tools/list` / `tools/call` / `ping` 的消息处理（直接调用处理函数，不依赖 subprocess 管道）；
- CLI：参数解析、退出码、JSON 输出；
- **分析侧**：健康评分（五维权重、扣分证据、等级边界、置信度与完备度）、诊断假设排序与缺失证据、重复/家族缺陷聚类、派生指标、三类报告渲染（无残留占位符）、分析 MCP 协议（`tools/list` 与 `spec/analysis-tools.json` 逐项一致）、分析 CLI 与确定性（同输入两次输出一致）。

新增/修改接口后至少补充：该工具的 mock 调用成功用例、必填参数缺失的失败用例、分页或过滤用例；新增工具时同步修改「26 个数据工具」/「7 个分析工具」相关断言。测试不依赖外网、不依赖真实凭证。

## 八、版本管理建议

| 对象 | 位置 | 规则 |
|---|---|---|
| 专家包版本 | `identify.md` frontmatter `version` | 语义化版本；编排流程或回答模板有实质变更时递增（当前 `1.1.0`） |
| 子技能版本 | 各 `SKILL.md` frontmatter `version` | 独立递增；修改工具表/口径时至少 patch |
| 数据 spec 版本 | `spec/interfaces.json` `specVersion` | 接口字段修订递增；破坏性变更（改名/删参数）用 major |
| 分析 spec 版本 | `spec/analysis-tools.json` `specVersion` | 分析工具参数/返回变化时递增；bundle 破坏性变更需与 schema 同步 |
| **评分卡与规则库** | `config/scorecard.json`、`config/diagnosis_rules.json`（分析技能内） | **算配置不算契约**：调权重/阈值/规则可直接改并 patch 技能版本；但每次调整必须在发布说明中写明「依据、样本、校准人」，并保留旧版备份 |
| 构建产物 | `dist/checksums.txt` | 与发布版本一起归档，记录对应 git/tag 与发布日期 |
| 变更记录 | 建议在 `docs/` 或发布说明中维护 changelog | 写清「改了什么、依据哪份文档、影响哪些技能」 |

发布节奏建议：spec 与技能改动先在小范围（测试环境 + Mock）验证 → 跑构建与 unittest → 按顺序发布 12 个子技能（2 底座 → 6 业务 → 3 深能力 → 1 总控）→ 更新平台专家包（确认技能列表版本）→ 归档 dist 与 checksums。评分卡/规则库的业务校准单独走一次「配置变更 + 回溯验证」，不与代码发布混在一起。

## 九、开发约定与禁止事项

**约定**

- 仅使用 Python 标准库；Python 3.10+ 风格代码（构建脚本兼容 3.9）；所有文本 UTF-8（无 BOM）。
- Windows 兼容：路径统一用 `pathlib` / `os.path`，zip 内路径一律 `/`；不依赖 shell 特性。
- 凭证只从环境变量读取，日志中掩码；真实数据不入库、不入包、不进文档。
- 业务口径写在技能 `references/` 或 `SKILL.md`，代码只做数据获取与归一。
- 改共享契约（spec / manifest / identify）前先与 Lead 对齐，改后跑全量校验。

**禁止**

- 在 MCP Server / CLI / 技能脚本中硬编码 appKey、appSecret、Token、网关地址。
- 绕过 spec 在多个技能或代码里复制接口 path/字段定义。
- 把业务判断逻辑写进 MCP Server（它只负责协议、鉴权、传输、错误归一）。
- **让 LLM 算分/算指标**：评分、统计、阈值判断、聚类、模板渲染必须由分析 MCP / `analysis_cli.py` 完成；提示词里出现「自己算一下」属违规。
- **分析工具取数或访问网络**：分析引擎只接收 bundle，不调用 26 个数据接口、不读凭证、不读时钟；破坏纯函数性会毁掉可复现与可审计。
- **手工复制分析资产**：`config/scorecard.json`、`config/diagnosis_rules.json`、`templates/*.md`、`assets/demo_bundle.json` 只放在 `substation-analysis-mcp` 技能内；其他技能不得携带（构建脚本会拦）。
- 手动修改 `dist/` 产物（必须由 `build_pack.py` 生成，保证可追溯与 checksum 一致）。
- 在技能 zip 内放 `dist/`、缓存、日志、数据文件；单包超过 10MB。
- 未登记就把接口说明整段塞进每个技能（上下文成本与维护成本都会失控，见 [05-架构设计](05-架构设计.md) 的反模式清单）。
