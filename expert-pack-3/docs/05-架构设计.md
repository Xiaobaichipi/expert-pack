# 05 · 架构设计

> 面向后续接手人的架构说明（ADR 风格）。记录「为什么这么设计」「哪些是刻意不做的」，以及演进触发条件。

## 一、背景与约束

| 约束 | 说明 | 对设计的影响 |
|---|---|---|
| 交付形态 | skillhub 专家包 = 轻量文本包（v1.1.0 为 12 个技能独立安装，单包 ≤ 10MB） | 不引入二进制依赖、不打包数据/模型；技能必须可独立发布 |
| 上下文成本 | 专家包注入 LLM 上下文，技能越多、`SKILL.md` 越长，Token 成本越高 | 分层按需加载；长内容下沉到 `references/`；不拆 26 个技能 |
| 鉴权未就绪（真实凭证） | 26 个 PMS 接口的中台凭证仍在申请；二期已内置本地可鉴权模拟网关 | 默认 `mock` 适配器；鉴权可插拔；AppKey 签名集中在 `pms_client/signing.py`（模拟规范，真实规范下发后替换该实现）；`pms_cli.py mock-server` 可走通 token/appkey 全链路 |
| 接口规格为推断值 | 接口地址、参数、返回字段来自原始说明文档与命名惯例推断（`spec.status = inferred`） | 契约集中在 spec，接口修订只改一处；Mock 与真实接口同构 |
| 专业口径 | 变电问数涉及缺陷率、检修及时率、可靠率等指标口径 | 口径写在技能层（话术/参考），不写死在代码 |
| **计算可信** | 健康分、缺陷率、根因排序若由 LLM 心算，不可复现、不可审计 | 计算全部下沉到分析 MCP（Python 确定性函数）；LLM 只传参与解读 |
| **历史数据仅约 2 年** | 趋势/预测样本不足 | v1.1.0 明确不做趋势与预测；指标接口预留 `trend` 字段并返回 `null` + `dataGaps` |
| **知识库已就绪但工具名依平台** | 内网 WeKnora 知识库已通过 MCP 调通，工具命名由平台决定 | 契约只约定 `knowledgeQueries`/`citations` 语义，不绑定工具名 |
| **生产平台为内网腾睿work** | AgentScope 智能体平台（含前端），支持 MCP 挂载 | MCP 必须 stdio、无参数、stdout 纯协议；配置以平台表单为准 |
| Windows 环境 | 交付与运行环境为 Windows | 纯标准库、路径兼容、UTF-8、zip 内 POSIX 路径 |

## 二、架构分层

```
┌──────────────────────────────────────────────────────────────────────────┐
│ L0 知识层                                                                 │
│   WeKnora 知识库 MCP（平台已配置、已调通）                                 │
│   职责：按查询语句检索规程/标准/反措片段；不参与计算、不生成业务结论        │
└───────────────────────────────▲──────────────────────────────────────────┘
                                │ knowledgeQueries → citations（片段保真）
┌───────────────────────────────┴──────────────────────────────────────────┐
│ L1 编排层                                                                 │
│   identify.md（专家包编排提示词） + substation-qa-orchestrator（问数总控）│
│   职责：意图识别 → 八类意图路由 → 设备主键归一 → 跨域组合 → 五段式回答    │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ 只在需要时调用对应领域/深能力技能
┌───────────────────────────────▼──────────────────────────────────────────┐
│ L2 领域能力层（6 个业务技能，各自独立可安装）                              │
│   substation-asset-ledger（设备档案，5 接口）                             │
│   substation-device-tree（设备树导航，2 接口）                            │
│   substation-om-health（缺陷/隐患/故障，4 接口）                          │
│   substation-maintenance-test（检修/方案/修试/巡视/试验，6 接口）         │
│   substation-reliability（可靠率/停电/可开放容量，3 接口）                │
│   substation-resource-topology（智能装备/仪表/厂家/专题图/电源/范围，6 接口）│
│   职责：业务语义、参数口径、典型问数→工具组合、结论模板                    │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ 取数结果按 bundle schema 组装
┌───────────────────────────────▼──────────────────────────────────────────┐
│ L2.5 分析层（深能力技能 + 分析底座，v1.1 新增）                            │
│   substation-health-assessment（健康评估：assess_device_health /          │
│       assess_station_health / compute_device_metrics）                    │
│   substation-diagnosis（诊断：diagnose_equipment / detect_defect_patterns）│
│   substation-report（报告：generate_report / list_report_types）          │
│   substation-analysis-mcp（7 个确定性分析工具的 MCP/CLI 实现）             │
│   输入：bundle（spec/analysis-bundle.schema.json）；输出：评分/假设/证据链 │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ 统一经网关调用（不直连数据库）
┌───────────────────────────────▼──────────────────────────────────────────┐
│ L3 接口网关层                                                             │
│   pms-gateway-mcp：SKILL.md（用法/错误码/排障） + MCP Server + CLI         │
│   pms_client：spec / client（门面 call_tool）/ 错误归一 / Mock            │
│   职责：26 个工具的统一入口、参数校验、分页、错误码、Mock、协议适配        │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ 端口-适配器边界
┌───────────────────────────────▼──────────────────────────────────────────┐
│ L4 适配层                                                                 │
│   transport（urllib：GET query / POST json body / path 替换 / 超时 / 重试）│
│   auth（AuthProvider：mock / none / appkey / token 四种策略）             │
│   mock（按 spec.tools[].mock 返回同构样例，支持过滤/分页）                 │
│   config（环境变量 → PmsConfig；spec 路径定位）                           │
└──────────────────────────────────────────────────────────────────────────┘
```

**一次问数的数据流**：用户问题 → L1 意图路由与实体抽取 → L2 选定领域技能、生成工具调用参数 → L3 `call_tool` 校验参数、按 spec 拼请求 → L4 鉴权 + 传输（或 Mock 短路）→ 返回归一 → L2 组织业务结论 → L1 汇总口径、来源接口编码与局限，输出五段式回答。

**一次深度分析的数据流**：用户问题 → L1 判定为深度分析意图 → L2 取数（多次 `call_tool`）→ 按 bundle schema 组装数据包 → L2.5 分析技能调用分析 MCP 计算（评分/诊断/指标）→ 若返回 `knowledgeQueries` 则经 L0 知识库检索得到 `citations` → `generate_report` 渲染报告 → L1 组织「结论 → 证据 → 置信度与缺口 → 引用 → 建议」。

**关键边界**：L2 不写 HTTP、不读环境变量；L4 不懂业务语义；L3 不做业务判断；L0 只检索不计算。接口字段只存在于 spec，bundle 字段只存在于 bundle schema，L2/L3/L4/L2.5 均不得自造字段。

## 三、关键决策与理由

### D1 契约优先：spec/interfaces.json 作为单一事实源

- **决策**：26 个接口的工具名、编码、method/path、参数、返回提示、Mock 数据全部集中在 `spec/interfaces.json`；MCP schema、CLI、Mock、文档映射表由它派生。
- **备选**：各技能/代码内各自维护接口定义；或每个接口一个 JSON。
- **取舍**：集中式契约让接口修订只改一处、支持并行开发（后端/技能/文档可同时按契约推进）、便于自动校验；代价是 spec 成为共享热点，改动需评审，且需要构建脚本防止漏改（如 `EXPECTED_TOOL_COUNT`）。底座技能发布 zip 内置的 `references/interfaces.json` 快照由构建脚本注入并校验字节一致，是打包产物而非第二事实源，用于满足 skillhub「装完即用」的独立安装诉求。

### D2 端口-适配器：Transport / AuthProvider 可插拔

- **决策**：传输与鉴权抽象为端口，`urllib` 传输、四种鉴权策略是适配器；Mock 是测试适配器，与真实适配器同构。
- **备选**：直接在 `client` 里写死 `requests` + if/else 鉴权；或用第三方 HTTP 框架。
- **取舍**：鉴权到位只需新增/补全适配器（appKey 签名只改一个函数），业务代码零改动；Mock 让无凭证联调成为常态；代价是多一层抽象，简单场景读代码略绕。不引入第三方库是为了满足 Windows 交付与 skillhub 轻量包约束。

### D3 门面 + 策略：统一入口 `call_tool`，鉴权按模式选策略

- **决策**：所有调用经 `client.call_tool(name, params)` 门面，鉴权由 `create_auth_provider` 按 `PMS_AUTH_MODE` 选策略；CLI/MCP 共用同一门面。
- **备选**：MCP Server 与 CLI 各自实现调用逻辑；按工具生成 26 个独立传输函数。
- **取舍**：单一入口保证参数校验、错误归一、日志/脱敏、Mock 行为一致，26 个工具零重复代码；显式方法只是门面的薄包装（便于 IDE 发现）。代价是门面成为关键路径，改动需全量测试。

### D4 编排 / 管道：0–8 步工作流，问数总控做路由与组合

- **决策**：`identify.md` 定义 9 步工作流（v1.0 为 0–6 步；v1.1 增加「组装数据包」「深度分析」「知识增强」三步，成为 0–8）：环境自检 → 意图路由 → 主键归一 → 取数 → 口径校准 → 组装 bundle → 深度分析 → 知识增强 → 结果组织/报告交付；`substation-qa-orchestrator` 负责意图路由、澄清与跨域组合；6 个领域技能各管一段取数，3 个深能力技能各管一段分析。
- **备选**：一个巨型技能塞下 26 个接口与全部业务口径；或完全自由让 LLM 自行编排。
- **取舍**：分层编排降低单次上下文长度、明确每步输入输出、便于定位「哪一步取数/口径/计算出错」；代价是跨域问题需要多次调用与汇总，延迟略高。领域技能之间不直接互调，统一由总控串联，避免网状依赖。

### D5 降级：MCP 优先，CLI 兜底

- **决策**：宿主挂载 MCP 时优先走 MCP 工具；未挂载/宿主不支持 stdio 时用 CLI 子命令兜底；两者共用 `call_tool` 与 spec。
- **备选**：只做 MCP；或只做 CLI。
- **取舍**：覆盖 Claude Desktop / Claude Code / OpenClaw 等宿主，也允许在终端与脚本中复现问题；代价是两条入口需要保持行为一致（由共用门面与同一套测试保证）。

### D6 关注点分离：SKILL.md（话术）/ references（口径）/ scripts（代码）

- **决策**：`SKILL.md` 只写角色、场景、工具清单、调用流程与输出格式；长口径、字段字典、问数模板放 `references/`；真正逻辑在 `scripts/`。
- **备选**：全部写进 `SKILL.md`；或把口径写进代码常量。
- **取舍**：`SKILL.md` 控制在 250 行内以降低上下文成本，细节按需加载；口径变更不改代码、代码变更不影响话术。代价是技能内文件更多，引用需保持同步（靠评审与构建校验）。

### D7 为什么不做重架构（不做微服务 / 重 DDD / 事件驱动 / 26 技能拆分）

- **决策**：保持「文本包 + 轻量 Python 客户端」；不拆微服务、不引入消息队列/事件总线、不按接口拆 26 个技能、不建领域实体聚合根。
- **备选**：每个接口一个技能（26 个）；每中心一个微服务；完整 DDD 分层与事件驱动。
- **取舍**：
  - 26 个技能会让每次问数注入大量无关技能描述，Token 成本与选择错误率都上升；按**业务主题**聚成 6 组更符合问数意图。
  - 26 个接口的复杂度不足以支撑微服务/事件驱动的运维成本；当前瓶颈是鉴权与字段准确性，而非吞吐。
  - 轻量包更容易在 skillhub 发布、独立安装、快速迭代；重架构等真实需求出现再演进（见第五节触发条件）。

### D8 分析能力做成 MCP，而不是提示词

- **决策**：健康评分、诊断规则匹配、缺陷聚类、派生指标、报告渲染全部实现为 `substation-analysis-mcp` 的 7 个确定性工具（纯 Python 函数 + 配置文件），LLM 只负责组装输入、传参与解读输出。
- **备选**：把评分规则、阈值、模板写成提示词，让 LLM 现场「算」和「写」；或者每个深能力技能各写一套脚本。
- **取舍**：
  - **可复现**：同一 bundle 必得同一结果，可回归、可审计、可版本比对；LLM 心算做不到，且会随采样漂移。
  - **可校准**：权重/阈值放 `config/scorecard.json`、规则放 `config/diagnosis_rules.json`，业务专家调参不改代码。
  - **可测试**：工具函数能写单元测试（等级边界、扣分规则、置信度、占位符残留），提示词不能。
  - **可复用**：MCP 与 CLI 共用同一引擎，宿主挂了 MCP 就用 MCP，没挂就 CLI 兜底，行为一致。
  - 代价：多一个 Server 与一层协议；新增分析规则要动配置/代码并过测试，比「改一句提示词」重——这是刻意接受的成本，因为**计算错了比慢更严重**。

### D9 bundle 契约解耦数据与分析

- **决策**：数据侧与分析侧之间只通过 `spec/analysis-bundle.schema.json` 定义的数据包（bundle）交互：数据 MCP 返回原始接口结果，由 Agent 按 schema 组装成 bundle，再传给分析工具。分析引擎不认识 26 个接口，数据侧也不认识评分卡。
- **备选**：让分析工具自己去调数据接口取数；或让数据 MCP 直接返回「已算好的分数」。
- **取舍**：
  - **解耦演进**：接口 path/参数变化只影响数据侧与组装映射；评分卡/规则变化只影响分析侧，两侧可并行开发、独立测试。
  - **纯函数性**：分析引擎不访问网络、不读凭证；时间基准取 `bundle.timeWindow.end` 或调用方显式传入的 `as-of`（仅报告的 `generatedAt` 读取系统时钟），输入确定则输出确定，便于审计与复现。
  - **可解释**：bundle 里的 `sourceMeta` 保留每个数据来源的接口编码与参数，扣分/假设的证据链能一路追回到接口。
  - **缺口可见**：bundle 缺段不由引擎补齐，而是输出 `dataGaps`/`completeness` 并降低置信度——**宁可说不全，不可假装全**。
  - 代价：bundle 由 Agent 组装，组装质量依赖提示词与示例；为此在技能 references 与 docs/06 中提供逐字段映射表，并由构建脚本校验 schema 结构。

### D10 知识库只提供检索、不参与计算

- **决策**：WeKnora 知识库 MCP 在链路中的唯一职责是「按查询语句返回原文片段」。分析工具只输出 `knowledgeQueries`（检索建议），由 Agent 调知识库取回片段，整理为 `citations[{title, source, snippet, kbId}]` 后再传给 `generate_report`。知识库内容**不得**作为评分、指标、聚类、诊断打分的输入。
- **备选**：让分析引擎直接连知识库检索并计入分数；或让 LLM 用知识库内容自行改分；或不设引用、直接凭记忆写条款。
- **取舍**：
  - **数值可审计**：分数只来自 bundle 数据与规则库，知识条款只影响「依据与建议」章节，责任边界清晰。
  - **引用可追溯**：每个条款引用都有 `source`/`snippet`/`kbId`，检索不到就写「未检索到相关条款」，杜绝编造标准条文。
  - **平台解耦**：知识库工具名随平台而变，本包只约定语义（检索/取原文/列库），不绑定具体工具名，换平台只改平台侧映射。
  - 代价：链路多一跳（分析 → Agent → 知识库 → 报告），且知识增强是可选项；未挂知识库时必须显式降级并注明「未引用规程条款」。

## 四、效率与资源收益

- **Token 按需加载**：L1 只携带编排提示词；L2 业务技能与 L2.5 深能力技能在路由命中后才进入上下文；细节口径与 schema 说明按需读 `references/`。
- **技能可复用**：6 个业务技能与 3 个深能力技能都是独立交付物，可被其他专家包/会话直接安装复用（如只装「设备台账」或只装「健康评估」）。
- **契约先行**：接口文档下发前即可并行开发技能话术、Mock、文档与测试；接口修订只改 spec + 网关层，技能层通常不动。分析侧同理：`analysis-tools.json` 与 bundle schema 先定，引擎、技能、文档、测试并行推进。
- **Mock 支持无鉴权联调**：无凭证即可跑通 26 个工具、验证 schema 与问数链路，缩短鉴权等待期的空转。
- **分析侧零依赖演示**：`analysis_cli.py demo` + 内置 `assets/demo_bundle.json`，无需接口、凭证、知识库即可验证「评分 → 诊断 → 报告」全链路。
- **确定性交付**：构建脚本幂等、产物字节稳定（固定 zip 时间戳），checksums 可逐版本比对，便于审计与回滚；同一 bundle 两次分析输出一致。
- **单一入口降低重复**：26 个工具共享校验、重试、错误归一与脱敏逻辑，新增接口的成本接近「加一条 spec」；7 个分析工具共享证据链、置信度与知识检索建议的生成逻辑。
- **业务可自校准**：评分卡与诊断规则是配置，业务专家可在不碰代码的前提下调权重/阈值并回溯验证，缩短「模型校准」往返周期。

## 五、演进路线（按触发条件，不提前做）

| 演进项 | 什么时候该做 | 要做的最小版本 |
|---|---|---|
| 指标层（指标库/口径字典） | 出现跨技能重复计算同一指标（缺陷率、检修及时率、可靠率），或口径争议频繁（v1.1 已有 `compute_device_metrics` 的 8 类派生指标作为起点） | 在 L2 之上增加指标定义文件（口径、分子分母、时间窗、数据来源接口），由总控引用；暂不建服务 |
| 趋势与预测 | 历史数据积累到足以支撑同比/趋势（当前仅约 2 年），且业务明确要求预测 | 先在 `compute_device_metrics` 补齐 `trend` 的确定性算法（同比/环比/移动平均），仍不引入 ML 模型；预测结果必须标注数据年限与外推风险 |
| 评分卡业务校准 | 准备正式上线，或有业务专家提出权重/阈值异议 | 用真实历史样本回溯校准 `config/scorecard.json` 与 `config/diagnosis_rules.json`，留档「依据/样本/校准人/版本」；不改代码 |
| 决策优化 | 用户从「先修哪台」升级为「在预算/停电窗口约束下怎么排」 | 在规则建议之上增加排序/约束求解（可独立工具），输出必须附带约束与假设，仍由分析 MCP 承载 |
| 缓存层 | 同一设备/同一站的高频重复查询占比明显，或接口 QPS 成为瓶颈 | 在 `client` 加 TTL 内存缓存（按工具+参数键），支持强制刷新；先单机、后共享 |
| 网关聚合（BFF/组合接口） | 单个问数需 5+ 次串行调用、延迟不可接受，且中台允许组合查询 | 在 L3 增加组合工具（如「设备画像」一次返回台账+缺陷+检修摘要），仍走 `call_tool` 与 spec |
| 可观测性 | 多环境/多团队使用，问题定位成本上升 | 结构化调用日志（工具、耗时、错误码、脱敏参数）、调用量/QPS/错误率统计；不记录凭证与敏感明细 |
| 脱敏与权限中间件 | 对外交付或跨部门共享，出现敏感字段/越权数据风险 | 在 L3 增加输出脱敏与数据范围校验钩子（手机号/身份证/地址掩码、组织范围过滤），按角色配置 |
| 实时量测接入 | 用户开始问「当前负载/当前状态」而可靠性接口无法满足 | 单独对接遥测/遥信通道（原始文档 3.2 建议），作为新能力域技能，不混入现有 26 接口 |
| 知识治理（引用质量） | 知识库文档版本频繁更替，或出现引用过期/冲突 | 引用记录增加文档版本与检索时间，建立条款生效/失效标注与人工复核流程；仍只做检索，不参与计算 |
| 接口数量显著增长（如 50+） | 技能内工具表过长、路由准确率下降 | 重新划分业务分组与技能边界；考虑按中心/主题分层检索，而非按接口拆技能 |

## 六、反模式清单（明确禁止）

1. **把 26 个接口说明全塞进每个技能**：上下文爆炸、口径漂移；接口说明只保留在 spec 与网关技能，业务技能只引用所需工具。
2. **把业务逻辑写进 MCP Server**：MCP Server 只做协议、鉴权、传输、错误归一；业务判断属于 L1/L2，否则无法复用、测试与演进。
3. **鉴权硬编码**：凭证写进代码/文档/配置示例（真实值）；必须环境变量 + 掩码日志。
4. **绕过 spec 在各处复制字段**：在技能、测试、文档里手抄 path/参数名会形成多份事实源；应引用 spec 或由构建/测试校验一致性。
5. **按接口拆技能**（26 个）：增加上下文成本与路由噪声；按业务主题拆分。
6. **在 dist/ 里手改产物**：不可追溯、checksum 失效；必须由构建脚本生成。
7. **为「以后可能用到」提前上重架构**：没有触发条件不做服务化/事件驱动/缓存集群。
8. **编造缺失数据**：接口空结果/失败时用推测值补齐，是数据类应用最严重的问题；坚持「未取到数据」并给下一步建议。
9. **让 LLM 算分/算指标**（v1.1 新增）：评分、统计、阈值、聚类、模板渲染必须由分析 MCP 完成；提示词里出现「自己算一下」即违规——不可复现、不可审计、不可回归。
10. **分析引擎取数或联网**（v1.1 新增）：分析工具接收 bundle，不调用数据接口、不读凭证、不读时钟；一旦破坏纯函数性，证据链与确定性同时失效。
11. **用知识库内容改分数**（v1.1 新增）：知识条款只进「依据/建议/引用」，不参与评分与诊断打分；知识库检索不到就如实声明，不得编造条款号或条文。
12. **让分析资产散落**（v1.1 新增）：`config/scorecard.json`、`config/diagnosis_rules.json`、`templates/*.md`、`assets/demo_bundle.json` 只属于分析底座技能，其他技能不得复制携带（构建脚本会拦）。
