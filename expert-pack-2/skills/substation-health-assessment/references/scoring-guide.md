# 健康评估专家 · 评分卡解读指南

> 本文件是 `substation-health-assessment` 的细节层，供「拿到分析工具返回值之后怎么写解读」时查用。
> 事实源优先级：`spec/analysis-tools.json`（工具契约）> 分析引擎 `config/scorecard.json`（权重与阈值）> 本文件（解读话术）。
> 本文中的权重与阈值是 `default` 档的**示意口径**，用于向用户解释「扣在哪」；**任何分数、维度分、扣分额都以工具返回值为准**。

## 一、评分卡结构

### 1.1 五维度模型

| 维度 | 默认权重 | 数据来源（bundle 字段） | 缺数据时 |
|---|---|---|---|
| 缺陷 | 0.30 | `defects[]` | 维度不计分，`dataGaps` 记「defects 缺失」 |
| 故障 | 0.25 | `faults[]` | 同上 |
| 修试 | 0.20 | `tests[]` | 同上 |
| 负载 | 0.15 | `load{}` | 同上 |
| 台账 | 0.10 | `device{}` | 按缺失字段逐项扣，不整维跳过 |

每维 0-100 起扣、单维最多扣满 100；总分 = Σ(维度分 × 权重)，再由引擎四舍五入并定级。**这条公式只用于解释，不得由 LLM 执行。**

### 1.2 `assess_device_health` 返回字段含义

| 字段 | 含义 | 解读要点 |
|---|---|---|
| `score` | 0-100 总分 | 保留 1 位小数；不要二次取整成整数 |
| `grade` / `gradeLabel` / `risk` | A-E / 健康度标签 / 风险 | 三者必须一起引用，不可只报分数 |
| `dimensions[]` | 各维度得分与权重 | 用于说明「哪个维度拖后腿」，不重算加权 |
| `deductions[]` | 扣分明细（规则ID/维度/扣分值/依据/来源接口） | 每条都要能对上数据，见第四节 |
| `completeness` | `present/total` | 写作「完备度 x/5」 |
| `confidence` | 0.30-0.95 | 决定结论可用性档位，见第三节 |
| `summary` | 引擎生成的一句话结论 | 可引用，不得改写成更强的判断 |
| `knowledgeQueries[]` | 知识检索建议 | 交 WeKnora MCP 检索，不得自行编条款 |

## 二、分数与等级含义

| 等级 | 分数 | 标签 | 风险 | 专业含义 | 推荐动作 |
|---|---|---|---|---|---|
| A | ≥90 | 健康 | 低 | 各维度基本无扣分，数据齐全 | 正常周期巡视检测 |
| B | ≥80 | 良好 | 低 | 个别记录性扣分（一般缺陷/单次超期） | 按计划消缺，关注趋势 |
| C | ≥70 | 注意 | 中 | 存在明确薄弱环节（严重缺陷未闭环、试验超期等） | 纳入近期检修计划、专项检查 |
| D | ≥60 | 预警 | 较高 | 多维度叠加扣分 | 尽快安排专项检查与消缺，评估运行方式 |
| E | <60 | 严重 | 高 | 复合风险（如危急缺陷 + 故障 + 试验不合格） | 优先处置、必要时限制运行方式并上报 |

**表述约束**

- 等级是「健康度分级」，不是「设备合格/不合格结论」，禁止写成「设备不合格」「设备报废」。
- C/D/E 表述为「健康度偏低/预警/严重，建议…」，不得表述为「必然故障」「一定会跳闸」。
- 分数波动必须用同一 `scorecard_profile`、同一时间窗、同一数据截止时间比较；口径不同则并列展示并说明。

## 三、置信度与完备度

### 3.1 计算口径（用于解释，不用于手算）

基础 0.9；`defects` / `faults` / `tests` / `load` 每缺一节 -0.05（最多 -0.4）；`timeWindow.end` 距评估基准（`--as-of` 或 `timeWindow.end`）超 180 天 -0.1；结果 clamp 到 0.30-0.95。
`completeness = {present: n, total: 5}`（device 恒计入 + 上述四节）。

### 3.2 分档与披露模板

| 区间 | 档位 | 模板 |
|---|---|---|
| ≥0.85 | 高 | 「数据完备度 x/5，置信度 0.xx（高），结论可作常规决策参考，最终以业务复核为准。」 |
| 0.70-0.84 | 中 | 「数据完备度 x/5，置信度 0.xx（中）；缺 {缺口项}，补数后建议重算，暂不作考核依据。」 |
| 0.55-0.69 | 偏低 | 「置信度 0.xx（偏低），本次评分只能提示方向，不能作为停电/检修/考核决策依据。」 |
| <0.55 | 低 | 「数据不足以定级：仅列出已取到的事实与补数清单（见 dataGaps），不给出健康等级结论。」 |

### 3.3 低置信度硬约束

1. 不得在句首直接给「健康/不健康」定性；必须先写「数据不足」。
2. 不得把低置信度的 E/D 级写成「设备存在重大隐患」——只能说「按现有数据评分偏低」。
3. 必须给出补数清单（缺哪个域、对应哪个接口、补什么字段）。
4. 报告交付时，「置信度」一节不得省略。

## 四、扣分证据表范式

### 4.1 字段对齐

`deductions[]` 每条包含：`ruleId`（规则ID）、`dimension`（维度）、`delta`（扣分值，负数）、`reason`（扣分原因）、`source`（来源接口编码数组）、`data`（依据数据摘要）。
输出表格列固定为：**规则ID | 维度 | 扣分 | 依据数据 | 来源接口**。

### 4.2 填写规范

- 扣分额与 `delta` 逐字一致（含负号），不得四舍五入或换算成百分比。
- 依据数据写「记录标识 + 关键字段值」，如「DF-2026-0001 危急 状态=待处理 发现 2026-09-01」。
- 来源接口写 `interfaceCode`（如 `pgp-106-2411-00703`），可附工具名 `inquire_defect`。
- 同一规则命中多项时，可合并成一行并在依据数据中列条数，但总数要与引擎返回的扣分值一致。

### 4.3 示例（表头即模板）

| 规则ID | 维度 | 扣分 | 依据数据 | 来源接口 |
|---|---|---|---|---|
| D-OPEN-CRIT | 缺陷 | -30 | 危急缺陷 DF-2026-0001 状态=待处理（发现 2026-09-01 08:00） | pgp-106-2411-00703 |
| D-OVERDUE | 缺陷 | -10 | 严重缺陷 DF-2026-0001 处理中 12 天（>7 天） | pgp-106-2411-00703 |
| F-12M | 故障 | -25 | FT-2026-0001 差动保护动作（2026-08-03） | pgp-106-2411-02603 |
| T-ABNORMAL | 修试 | -30 | RT-2025-0001 预试 结论=不合格（2025-04-11） | pgp-106-2411-05003 |
| L-HIGH | 负载 | -10 | loadRate=70.0 未触发；若 >80 则 -10 | pgp-108-2411-00201 |
| M-MISSING | 台账 | -20 | `assetId` 与 `psrId` 均缺失 | pgp-102-2411-00102 |

> 规则 ID 命名以引擎返回为准；上表仅示范写法，**新增规则 ID 属自造，不得使用**。

## 五、站级评分与报表口径

### 5.1 `assess_station_health` 返回解读

| 字段 | 含义 | 口径说明写法 |
|---|---|---|
| `station` | 站元数据（`stationId`/`stationName`/`voltageLevel`） | 与台账一致，不一致时并列 |
| `devices[]` | 每台设备分项结果 | 设备清单以 `list_psr_by_filters` 的 `total` 校验是否取全 |
| `aggregate.avgScore` | 站级平均分 | 均值为**纳入评分的设备**平均，不含数据不足以评分的设备（须注明台数） |
| `aggregate.gradeDistribution` | 等级分布 | 报「A/B/C/D/E 各 n 台」 |
| `aggregate.riskTop` | TopN 风险设备 | 报 TopN 数量与选取依据（`top_n` 参数） |
| `aggregate.criticalCount` | 危急/高风险计数 | 与缺陷域 `inquire_defect` 的危急未闭环数交叉核对 |

### 5.2 站级月报口径（交 `substation-report` 的 `station_monthly`）

1. **统计范围**：`station_meta` + 纳入设备台数 + 未纳入设备台数及原因。
2. **时间口径**：`timeWindow{start,end}` 与数据截止时间，可靠性指标另注 `statPeriod`。
3. **评分口径**：`scorecard_profile` 名称、权重是否为客户化配置。
4. **可比性**：跨月对比必须同 profile、同设备范围；设备范围变化时单独说明。
5. **风险清单**：列 `riskTop` 全部条目 + 每条的 `grade`、`score`、主要扣分维度、建议动作。
6. **数据质量**：站级置信度取参与评分设备的最低档或均值口径（写明用哪种），并列出站级 `dataGaps`。

## 六、常见误读清单（逐条禁用）

| 误读 | 正确做法 |
|---|---|
| 用分数自己判等级 | 只引用 `grade` |
| 把 avgScore 当站级等级 | 站级只报均值 + 等级分布 |
| 把「未查询到缺陷」当「无缺陷风险」 | 写「该时间窗内未返回记录」，并降低置信度 |
| 把 `deductions` 手算总和当总分 | 总分只取 `score` |
| 缺数据时按同类设备均值补齐 | 不补齐，列 `dataGaps` |
| 低置信度直接给「设备健康」结论 | 先声明数据不足，再给有限结论 |
| 把 `status=处理中` 当「未超期」 | 超期与否看引擎 `D-OVERDUE` 类扣分与等级时限 |
| 跨 profile / 跨窗口比较分数 | 并列展示并注明口径不同 |
| 用知识库条款改写分数 | 条款只解释规则，不改分 |
| 报告中省略置信度与缺口 | 必须保留，作为报告固定章节 |

## 七、自检清单（输出前逐项确认）

- [ ] 分数、等级、风险三段齐全，且都来自工具返回值。
- [ ] 每个扣分项都有规则ID、依据数据、接口编码。
- [ ] `completeness` 与 `confidence` 已披露，且与披露话术档位一致。
- [ ] `dataGaps` 原文列出，未用推测值补齐。
- [ ] 时间窗、主键、单位（MVA、%、天）全篇一致。
- [ ] 无「必然/一定/证明」等越界措辞；C/D/E 未写成「不合格」。
- [ ] Mock 模式已标注；敏感信息已脱敏。
- [ ] 涉及考核/停电/检修决策的结论已提示业务复核。
