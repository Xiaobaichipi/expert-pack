## 三、12 个问题：问句 → 接口 → 数据 → 分析

以下为演示脚本实际输出（已截断长字段），所有数字均由接口返回数据或分析引擎计算得到。

### Q1 220kV 郑州变电站有哪些主变？台账关键信息？

- **接口**：`list_asset_params(assetType=transformer, stationId=STA-220-01)`、`list_psr_by_filters(stationId=…)`
- **返回**：2 台主变（`AST-102-0001` 1号主变、`AST-102-0002` 2号主变，均 180MVA、SSZ11-180000/220、在运）；
  全站 5 个 PSR（变压器 2、断路器 2、隔离开关 1）。
- **分析**：主变型号/厂家/投运时间齐全，可支撑容量与家族性分析；全站设备类型分布清晰。

### Q2 实物 ID `UTC-2020-000123` 是哪台设备？供电路径与停电影响？

- **接口**：`get_device_by_utc_num`、`get_psr_by_id`、`query_svg_map_by_psr_id`、`search_power_path`、`analyze_supply_area`
- **返回**：1号主变（220kV 郑州变）；接线图 SVG 175 字符；路径「500kV 嵩山变 → 220kV 郑州变 → 1号主变」；
  停电影响 4 个对象、涉及 110kV 二里岗/城东两站，风险「较大」。
- **分析**：该主变停运影响 2 个 110kV 站的部分 10kV 负荷，检修需评估转供。

### Q3 当前有哪些严重缺陷？

- **接口**：`inquire_defect(defectLevel=严重)` + `view_defect`
- **返回**：2 条严重缺陷（1号主变套管 2026-09-12；110kV 二里岗 1号主变本体 2026-09-30），均未闭环。
- **分析**：套管缺陷与 8 月跳闸、套管区消防隐患相互印证，应优先处理。

### Q4 站内隐患与整改状态？

- **接口**：`list_hazard(stationId=STA-220-01)`
- **返回**：2 条——塔吊侵入（较大、整改中）、树木超高（重大、已闭环）。
- **分析**：较大及以上 2 条；塔吊外破风险需重点管控。

### Q5 检修计划与修试情况？

- **接口**：`get_repair_plan(stationId=…)`、`find_repair_test(pageSize=50)`（按 stationId 过滤）
- **返回**：计划 3 项（1号主变 A 类 2026-10-15、2201 断路器 B 类 2026-11-05 待执行；2号主变 C 类已完成）；
  试验 3 条均合格，最近 1号主变试验为 2025-04。
- **分析**：1号主变 9 月严重缺陷之后没有新的试验记录，需在 A 类检修中补做套管介损/电容量复测。

### Q6 主变负载与可开放容量？

- **接口**：`query_open_capacity(stationId=…)`
- **返回**：1号 180/126MVA（70.0%，可开放 54）；2号 180/98MVA（54.4%，可开放 82）。
- **分析**：未达 80% 重载阈值，但 1号主变 70% 偏高，检修停电需校核 N-1；全站可开放容量合计 136MVA。

### Q7 站可靠性与停电事件？

- **接口**：`query_station_scale_analysis`、`query_outage_incident`
- **返回**：可用率 99.982%、停电 2 次/1.42h、停电用户小时 320.5；事件表按站返回 1 条计划检修（影响 1260 户）。
- **分析**：可用率达标；事件表未覆盖全部统计口径（2 次 vs 1 条），使用时应标注数据缺口。

### Q8 1号主变健康度如何？扣分来自哪些证据？

- **取数**：`get_asset_by_id`、`inquire_defect`、`view_defect`、`list_hazard`、`list_fault_trip_records`、
  `find_repair_test`、`get_repair_plan`、`list_patrol_record`、`query_open_capacity`、`query_station_scale_analysis`（10 次调用）
- **分析引擎**：`assess_device_health(bundle, as_of=2026-09-30)`
- **结果**：**健康分 86.3 / B 良好 / 风险低**
  - 缺陷维度 75 分（扣 25）：严重缺陷未闭环 −15、超期 18 天（限值 7 天）−10
  - 故障维度 75 分（扣 25）：近 12 个月跳闸 1 次
  - 修试/负载/台账：各 100 分
- **分析**：扣分证据全部可回溯到接口记录（`sourceMeta` 记录 interfaceCode/工具/参数），无推测值。

### Q9 8 月跳闸的可能原因？（跨域证据链诊断）

- **接口**：同 Q8 组装 bundle；`diagnose_equipment(bundle)`
- **结果**：2 个假设——① 套管受潮/绝缘劣化（0.82 / 置信度 0.95 / 证据 4 条）；
  ② 机构箱/二次回路受潮（0.68 / 0.75 / 2 条）。
- **证据**：缺陷描述「套管…渗油」、故障「套管绝缘受潮」、巡视「1号主变套管渗油」。
- **建议**：停电做套管介损/电容量复测与末屏检查，结合 A 类检修一并处理。

### Q10 缺陷时空分布与重复/家族性缺陷？

- **接口**：`inquire_defect(pageSize=50)`；`detect_defect_patterns(window_days=365, family_min_count=2)`
- **分布**：等级 一般 3 / 严重 2 / 危急 1；站 郑州变 5 / 二里岗 1；月份 2026-09 4 条（占 2/3）。
- **模式**：重复簇 0、家族簇 0；引擎标注数据缺口「device_meta 缺少 model/manufacturer」。
- **分析**：严重/危急缺陷集中在 1号主变（套管）与 2202 断路器（灭弧室），呈聚集趋势；
  但当前 6 条记录不足以判定家族性缺陷，**不能据此下「无家族缺陷」结论**。

### Q11 站级健康画像与风险设备排序？

- **取数**：站内 5 台设备分别组装 bundle（共 51 次接口调用）；`assess_station_health(bundles, station_meta, top_n=5)`
- **结果**：站均分 91.7，等级分布 A3/B2；风险排序 2202 断路器 84.0 > 1号主变 86.3 > 2201 断路器 92.3 >
  2201 隔离开关 96.0 > 2号主变 100。
- **分析**：2202 断路器（危急缺陷「灭弧室」处理中）为站内首要风险设备；1号主变次之。

### Q12 生成设备画像报告？

- **接口**：Q8 的 bundle + 健康分 + 诊断 + 派生指标；`generate_report("device_profile", payload)`
- **结果**：68 行 Markdown 报告，含设备基本情况、健康度评估、扣分证据、诊断假设、建议。
- **说明**：报告 `generatedAt` 取系统时间（其余内容确定）；`dataGaps` 会显式列出「缺陷趋势无法计算」。

## 四、接口数据如何组装成分析 bundle

`tools/mock_qa_demo.py::build_bundle()` 的映射（与 `spec/analysis-bundle.schema.json` 对齐）：

| bundle 字段 | 来源接口 | 说明 |
|---|---|---|
| `device` | `get_asset_by_id` | `assetName→name`、`assetStatus→status`，psrId/utcNum 取自台账 |
| `defects` | `inquire_defect(deviceId)` + `view_defect` | `defectLevel→level`，`view_defect.defectDesc→desc` |
| `hazards` | `list_hazard(stationId)` | `hazardType→type`、`hazardDesc→desc`（站级隐患归入该设备 bundle，演示简化） |
| `faults` | `list_fault_trip_records(deviceId)` | `faultTime→time`、`cause/protectionAction→description` |
| `tests` | `find_repair_test(deviceId)` | 无 `items[]` 时用 `dataSummary` 参与诊断关键词匹配 |
| `repairPlans` | `get_repair_plan(deviceId)` | planId/planName/planTime/status |
| `patrolRecords` | `list_patrol_record(stationId)` | 站级巡视记录（演示简化） |
| `load` | `query_open_capacity(deviceId)` | 额定/当前/可开放容量与负载率 |
| `reliability` | `query_station_scale_analysis(stationId)` | **站级指标代理设备级**（演示简化，正式环境应取设备级可靠性） |
| `sourceMeta` | 所有调用 | `{interfaceCode, tool, params}`，供证据链回指接口编码 |
| `timeWindow` | 固定 | `2025-10-01 ~ 2026-09-30`，`as_of` 默认取 `end` |

分析引擎的输入约定见 `skills/substation-analysis-mcp/references/bundle-schema.md`；缺字段会记入
`dataGaps` 并降低置信度，**不会用推测值补齐**。

## 六、限制与后续

1. **数据是虚构的**：站名、设备、人员、厂家地址均虚构；不可用于真实业务判断。
2. **家族性缺陷**：判定需要同型号/同厂家 + 同部位的多台设备证据（`device_meta`）；当前接口能暴露该
   数据缺口，但不能替代真实台账。
3. **站级可靠性代理**：设备 bundle 的 `reliability` 暂用站级统计，正式接入应替换为设备级指标。
4. **报告时间戳**：`generatedAt` 取系统时间，归档时需固定分析基准。
5. **企业侧未验证**：真实签名规范、平台上传流程仍需企业环境实测（见 [docs/09](09-模拟网关与鉴权.md) 限制章节）。
6. 若要把「问数分析」作为演示交付，建议后续把 12 个问题固化为评测集（输入问题 → 期望指标区间），
   并加真实知识库引用做报告增强。
